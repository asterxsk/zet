Architecture

The workspace is layered. Each crate is built on the ones above it in the list, and the dependency arrow never points back down.

The in-tree dependencies are declared in Cargo.toml in that order, so the layering is readable without opening a single manifest.

zet-update is the exception to the ordering and is the only crate here published as a library in its own right. It depends on nothing in the workspace, and nothing in the workspace depends on it except the binary, which calls it for --version and for the two typed update flags.

Why it is split this way

The alternative — an app that owns the window and is called by it — is the shape most terminals have, and it makes the interesting half of the program untestable without a display. Everything below zet is built so that a test can drive it with no window and no GPU: open two tabs, press a key, assert which one is active.

Two boundaries carry most of that weight.

  • zet-input does not depend on winit. A user's keybinding is text like Ctrl+Shift+T in a config file, so a key has to be namable, parseable, and printable on its own. It is a piece of the configuration vocabulary before it is ever a piece of an event, and winit's key type cannot be that because it describes a platform event rather than something a person writes down.
  • zet-ui is pure computation on the CPU. It is handed a description of the window, it fills a frame with rectangles, and it answers where the user just clicked. Everything the chrome does can be asserted against a frame and a hit test.

The crates

zet-vt — the terminal engine

It turns a byte stream from a pty into a grid of styled cells and tracks which cells changed so the renderer can repaint the minimum. The layers, bottom up: the value types (color, attrs, cell), storage (row, grid), the byte-level parser, the terminal state machine, and damage tracking.

The parser is deliberately ignorant of terminal state. Everything that can be wrong about a terminal, from reflow to erase semantics, lives in the state machine where it can be tested against a real grid instead of against a byte sequence.

zet-pty — the process layer

A running child process attached to a pseudoconsole, and the bytes flowing in and out of it. It is written against windows-sys rather than a wrapper crate, because every wrapper in the ecosystem was eliminated for a specific reason — a missing creation-flags parameter, an inverted TerminateProcess result on Windows, a two-year-old dependency tree.

ConPTY has four behaviours that turn a straightforward read loop into a deadlock, and none of them are in its documentation. Closing the pseudoconsole blocks until its output has been drained. Closing the input half kills the child with 0xC000013A instead of letting it see end of input. A read on the output pipe never returns zero while the pseudoconsole is open. And ConPTY's own tree kill misses detached grandchildren, so a job object with KILL_ON_JOB_CLOSE is the only thing that reliably reaps them.

zet-config — the file and the two planes

This is the shared vocabulary for everything above it. It owns the colour type with the sRGB-to-linear conversion the renderer needs and the contrast arithmetic the design system is held to; Theme and Palette, which are the two planes Design keeps apart; and Config, the file, its defaults, its diagnostics, and the round-trip that preserves your comments.

The file is authoritative and the settings panel is a view over it, so this crate is the only writer. That is what makes "change it in the app" and "change it by hand" the same operation rather than two code paths that have to be kept in agreement.

zet-font — discovery and pixels

fontique for the system database and swash for the pixels, with the fallback policy supplied here rather than by a shaping layer. A terminal's grid is one glyph per cell at a fixed advance width; text does not wrap around a float, does not need kerning across a cell boundary, and must never ligate two characters into one glyph unless the user asked for it.

The rule that keeps the grid a grid: every cell is the width of the primary face's advance for M, forever. A fallback face that is proportional, or monospaced at a different pitch, draws its glyph centred in the cell and is allowed to overflow it. Scaling a fallback to fit would move the cell boundaries, and a grid whose columns move is not a grid.

zet-input — decoded input to stdin bytes

The seam between the windowing layer and the pty. Almost all of it is a table, and the table is the legacy VT / xterm one. Key and mouse encoding live there, plus the paste and focus sequences that a mode gates rather than a keystroke.

The kitty keyboard protocol is negotiated rather than configured: a program pushes a set of flags, and the terminal reports keys according to whatever is on top. That stack lives in the terminal engine, because the terminal is the only thing that sees a program ask — so the encoder takes the current flag set as an argument rather than holding one, and a key is encoded against the state of the program that is going to read it.

Which encoding a key gets is a table lookup with a rule on top. The functional keys keep their legacy sequences, because in the protocol's own table those are the sequences; keys the legacy table has no bytes for at all — the locks, PrintScreen, Pause, Menu, and F13 up — are reported the protocol's way always. Text keys move to CSI u when the program asked for all keys, or, when it asked only for disambiguation, when the key is one the legacy encoding cannot tell apart. The code point is the key before shift, which is the part a naive implementation gets wrong: a program matching ctrl+shift+a looks for the code of a, and a terminal that sends the code of A hands it a chord it will never match.

Report alternate keys is the one flag deliberately not implemented, and the bit is dropped rather than echoed back. The host does not carry the physical key, and claiming a feature that is not there is worse than the honest no that the protocol's set-then-query handshake exists to get.

zet-session — one running terminal

The join between the pty and the parser: one parser, the terminal it feeds, and the scrollback view over that grid, for one tab. Sessions owns several and hands out the tab numbers.

The reader is not here, because the pty already runs it. This crate adds a pump instead: a thread parked in the pty's chunk channel with a timeout, appending whatever comes back to a buffer this crate owns and calling the host's waker. The pump exists because nothing else can wait — a ConPTY output pipe never reports end of file while the pseudoconsole is open, so there is no future to await and no readiness to poll. Teardown stops the pump and joins it before the pseudoconsole is shut down, so a parked pump cannot keep a closed tab's child alive.

zet-render — a frame

It turns a terminal and an app into two arrays of rectangles. It owns the atlas, the glyph cache, and the device; it does not own the layout, which is zet-ui's, and not the state, which is zet-app's. The grid draws from the theme's ANSI palette and the chrome draws from the app palette, and the two are enforced before anything gets here.

zet-ui — the chrome

The titlebar, the tab strip, the caption buttons, the scrollbar, the settings panel, and the find bar. It holds a palette for the length of one call and has no way to name a theme at all, which is the strongest form of the two-plane rule: the crate cannot break it.

Three things it is not told, each a deliberate limit: nothing about the grid, no clock — the indicator's travel is measured against a time the caller supplies, because a transition that reads the clock cannot be asserted seventy milliseconds into itself — and no scrollback position or find-bar state, both of which change without the configuration changing.

zet-app — what a key does

The terminal's behaviour with every platform dependency taken out. It owns the tabs, the selection, the scroll position, the keymap, and the cursor's blink, and it decides what a key press means. When it needs a window, a GPU, a clipboard, or an event loop it returns a Command and the caller carries it out.

zet — the binary

The binary and nothing else. Every decision the terminal makes lives in a library below it, which is why the interesting parts of zet have tests and this crate has a main. What is here is the set of things that cannot be a library: the event loop, the window, and the modules that talk to Win32.

host is the event loop's callback and the only place the platform and the state machine meet. keys and mouse translate between the platform's events and the vocabulary zet-app speaks. clipboard, platform, and picture call Win32 directly — picture through GDI+, for the decoders — and are the only files in the binary with an unsafe block; the crate denies unsafe_code everywhere else.

zet-update — becoming the next version

It answers three questions: what am I running, is there something newer, and how do I become it. The path is a check against GitHub's latest-release endpoint, a download that verifies size and digest before anything is written, a stage beside the running executable, and a replacement on the next launch. Windows will not let a running executable be overwritten or deleted, but it will let one be renamed, and that is the entire mechanism.

The binary calls it, and only from two typed flags: zet --check-update asks and zet --update installs. Nothing checks on launch and nothing checks on a timer, so the current build never touches the network unless you type one of those. That is described in Privacy, and what verification does and does not prove is in Security.

The workspace

One workspace at the repository root, with members = ["crates/*"]. The shared manifest sets the version, edition = "2024", rust-version = "1.90", and the dual licence, and lists every dependency once so that a crate's manifest names only what it actually uses.

The release profile is tuned for throughput rather than for compile time: fat LTO, one codegen unit, panic = "abort", and stripped symbols. Dependencies are optimized even in a debug build, because the parser and the windowing stack are what make a dev build feel slow and rebuilding them is rare.

Testing

Every crate below the binary is built to be driven by a test with no window in sight, and the tests are where several of the project's rules are enforced rather than promised: that zet's own themes clear the ANSI contrast floor, that the chrome palette matches the values in DESIGN.md, that the default keymap only names actions that exist, and that every key name round-trips through its text form.

The tests that talk to GitHub are ignored by default, so a flaky network is never the reason a pull request looks broken. .github/workflows/ci.yml runs formatting, lints with warnings denied, and the workspace tests on every push and pull request.
