Info

Why zet exists, what the workspace is made of, and what is deliberately not built yet.

Why

Windows terminals each make you give something up. Windows Terminal is good but its rendering and configuration are Microsoft's to decide. Alacritty is fast but has no tabs and no settings UI. WezTerm has everything and needs its own manual. None of them let you own the part that matters.

There is also a correctness problem that only shows up when you live in a terminal. Full-screen TUI programs flicker on every repaint unless the terminal honors synchronized output. Alternate-screen apps leave artifacts on resize. Mouse reporting, truecolor, and hyperlinks work in some terminals and half-work in others. You notice the first time you run an agentic coding tool inside one.

zet owns its terminal engine end to end: the byte parser, the screen grid, the scrollback, the reflow, the damage tracking, and the renderer. Nothing about the character pipeline is borrowed. That is the point of the project, and the reason the rest of it exists.

The crates

The workspace is layered, and each crate is built on the ones above it in this list — except zet-update, which stands alone. None of them is on crates.io, including that one.

Eleven crates, in dependency order
CrateWhat it owns
zet-vtThe terminal engine: parser, grid, scrollback, reflow, damage
zet-ptyConPTY sessions and shell profile discovery
zet-configTOML configuration, themes, the ANSI palette, hot reload
zet-fontFont loading, rasterisation, the face chain and its fallback order
zet-inputKey and mouse encoding, chords and keybindings
zet-sessionA session: a pty and a terminal with a read loop between them
zet-renderThe wgpu renderer: the glyph atlas, the grid and chrome pipelines
zet-uiThe chrome's layout, and the embedded IBM Plex Sans it is drawn in
zet-appThe application state machine: tabs, commands, themes, selection
zetThe binary: the window, the event loop, and the frame host
zet-updateVersion identity, update checks, self-replacement

Architecture describes how the layers fit together and what each one is allowed to know.

Not built yet

The documentation states plainly what does not exist, because the status on the overview is the honest description of the code and a page that rounded it up would be worse than no page.

  • No update check on launch, and none is planned. zet --check-update reports whether a newer version exists and zet --update installs it, and those commands are the only things in zet that touch the network.
  • No Report alternate keys. The rest of the kitty keyboard protocol is there; this flag is dropped rather than echoed, because the host does not carry the physical key.
  • No library API. The crates are a workspace behind one binary, and none of them is published to crates.io; zet-update is structured as a standalone library but is not on the registry either.
  • No build for macOS or Linux. The pty layer is ConPTY, the window and clipboard layers are Win32, and the icon is compiled into the executable by a Windows resource compiler, so cargo build on either host fails at compile time. See Install.
