Start

Install

Download the installer from the latest release, or build zet from source — either as a bare binary or through the installer script in packaging/.

Neither artifact is code-signed

Every release carries two artifacts and a SHA256SUMS digest beside them: zet-<version>-x86_64-pc-windows-msvc.exe, which is the terminal and nothing else, and zet-<version>-setup.exe, which is the per-user installer built by packaging/zet.iss. Neither is Authenticode-signed, so SmartScreen warns on first run whichever way you get it. The digest file is the thing to check against.

Requirements

  • Windows 11. The process layer is ConPTY and shell discovery reads the Windows app-alias directory, WSL distributions, and Program Files. Nothing here is portable.
  • Rust 1.90 or newer, with the MSVC toolchain. The workspace sets rust-version = "1.90" and edition = "2024".

The installer itself has a floor of Windows 10 version 1809 (10.0.17763), because that is the first build with the ConPTY API the pty layer runs the shell under. Installing on anything older would produce a window that opens and a terminal that never starts.

Build

git clone https://github.com/asterxsk/zet
cd zet
cargo build --release
cargo test --workspace

That produces target/release/zet.exe, which is the whole program. It needs no assets beside it, because the chrome's fonts are compiled in.

The release profile is tuned for throughput rather than compile time: fat LTO, one codegen unit, and panic = "abort", so a release build is slower to produce than a debug one and worth it.

Run

zet                           # start the terminal
zet --directory D:\somewhere  # start its shell there
zet --help                    # print the usage
zet --version                 # print the version

There is no flag for a setting, because a flag for every setting would be a second place for the same truth. --directory earns its place because it is not a setting: it is where you were standing when you typed the command. It is what the installer's folder right-click menu passes, and it applies to every tab the window opens, because the window is what the directory was chosen for. The short form is -d.

An argument zet does not recognise is refused rather than ignored, so zet --maximised fails with a message instead of opening a window that did not do what you asked. A flag with nothing after it says so by name — zet --directory reports that it needs a directory, rather than reporting an unknown argument.

zet --version prints the version, the commit the binary was built from, and the target triple: zet 0.1.0 (4eb42e4, x86_64-pc-windows-msvc). Three things rather than one, because a version on its own does not identify a build — two binaries can both call themselves 0.1.0 and differ, and the one a bug report came from is the one that matters. A build with no repository behind it, from a source tarball, says unknown where the commit goes.

The installer

packaging/zet.iss is an Inno Setup script. Every release is built by running it, and the installer it produces is the one linked at the top of this page. To build it by hand you need Inno Setup 6.3 or newer on PATH as ISCC.exe:

cargo build --release -p zet
ISCC.exe /DVersion=0.1.2 /O"dist" /F"zet-0.1.2-setup" packaging\zet.iss

/DVersion must be the version Cargo.toml carries. The release workflow passes the tag it is releasing, having already checked that the two agree.

It installs for the current user only, into %LOCALAPPDATA%\Programs\zet, and it never raises a UAC prompt. PrivilegesRequired=lowest makes Setup decline elevation even when the account could have it, and the "install for all users" option is not offered. It writes an uninstaller, unins000.exe, into the same directory, and registers itself under HKCU so zet appears in Settings → Apps → Installed apps for that user alone.

Settings are never touched. %APPDATA%\zet\config.toml survives an uninstall, because reinstalling and losing your configuration is worse than leaving two kilobytes behind.

Three things are offered on the Select Additional Tasks page, and only the first is ticked by default.

There is no licence page. zet is MIT/Apache-2.0 dual-licensed, which grants rights rather than withholding them, so a page demanding that you click "I accept" would misrepresent what the licence says. The two licence files and THIRD-PARTY-NOTICES are installed beside the binary instead, which is where they belong: the binary statically links IBM Plex Sans under the SIL Open Font License, and that licence requires its text to travel with the font.

The icon is packaging/zet.ico. packaging/make-icon.py draws both the icon and zet.svg from one set of constants, so the two cannot drift.

Where it looks for configuration

%APPDATA%\zet\config.toml. A missing file is not an error; zet starts with its defaults. The settings panel writes to that file as you change a setting, and keeps its comments when it does. See Configuration.

The tests that need the network

The tests that talk to GitHub are ignored by default, because a test that needs the network is a test that fails on a train. cargo test --workspace does not run them. To run them on purpose:

cargo test -p zet-update --test live -- --ignored --nocapture

Releases

Releases are tags. There is no release branch and no manual build step: the version in Cargo.toml under [workspace.package] is moved, the changelog entries move out of Unreleased, and a v-prefixed tag is pushed.
.github/workflows/release.yml then checks that the tag and the manifest agree, builds the binary and the installer, writes a SHA256SUMS digest for each of them, and publishes a GitHub Release. Both artifacts are wanted: the bare zet-<version>-x86_64-pc-windows-msvc.exe is what the updater looks for by that exact suffix and replaces in place, and zet-<version>-setup.exe is what a person downloads the first time.

The tag and the manifest are checked against each other because a binary that reports a different version from the tag it shipped under makes the updater offer the same release on every launch, forever.

Archives are not Authenticode-signed. A checksum proves the download matches what the release published; it does not prove who published it. That distinction, and what stands in for signature verification today, is set out in Security.

Updates

Run zet --check-update and zet asks GitHub whether a newer version has been published, prints the answer, and exits. Run zet --update and it does the same check and then installs what it finds: it downloads the archive, checks it against the digest the release published, and puts it where the running binary is. The new version takes effect the next time zet starts.

Both are requests you typed, and they are the only two commands in zet that touch the network: nothing here checks on its own, at launch or at any other time, and there is no setting for one to gate — see the update section of Configuration.
